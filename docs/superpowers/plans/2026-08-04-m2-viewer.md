# M2 — Viewer: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `<GuidedTour>` renders a fetched tour fully navigable by mouse, keyboard and screen reader, emitting typed analytics events — deployed on the example app.

**Architecture:** Pure logic modules first (`navigation`, `personalize`, `events`/`session`), React components on top. Everything lives under `src/react/` and ships through the `/react` entry, which must keep importing **only React** — the entry-isolation guard test enforces it. Styling is plain CSS driven by `--gt-*` custom properties.

**Tech Stack:** React 19 function components (compatible with 18.3 — no `use()` or Server Component APIs), TypeScript strict, `bun test` + Testing Library + happy-dom, axe-core for a11y assertions.

## Global Constraints

- `/react` sources import nothing outside `react` (and type-only imports from `../queries`) — `test/exports.test.ts` fails otherwise. **Type-only imports from `../queries/types` are allowed** (they vanish at build time; the guard scans `from 'sanity...'` patterns only).
- Personalization tokens substitute into **text only, never `href`, `src`, or any URL-valued field** (spec §8.3). A regression test must exist and survive.
- Events union exactly as spec §8.4; `sessionId` from `crypto.randomUUID()`, in memory only — no cookies, no storage.
- Accessibility per spec §8.6 is a requirement: hotspots are `<button>`s with accessible names; step changes announce via `aria-live="polite"` and move focus to the step container; `prefers-reduced-motion` disables pulse and transitions; keyboard: ←/→, Space, Home, End, Escape; tooltips are disclosures with `aria-expanded`/`aria-controls`.
- CSS: one file `src/react/styles.css` (published from `assets/` by the existing `prebuild` — do not change that mechanism). All colors/sizes flow through `--gt-*` custom properties with defaults equal to the theme schema's initialValues (`--gt-accent: #2276fc`, `--gt-surface: #ffffff`, `--gt-text: #1a1a1a`, `--gt-overlay: #0f172a`, `--gt-radius: 8px`, `--gt-hotspot-size: 24px`, `--gt-font-family: inherit`). Class names are prefixed `gt-`.
- Responsive images: append `?w=<width>&auto=format&q=80` to the CDN URL; srcset widths `[640, 960, 1280, 1920, 2560]`. No image library.
- Types come from `sanity-plugin-guided-tours/queries` (`GuidedTourDoc` etc.) — never redefine them.
- All prior toolchain constraints hold (see memory `guided-tours-m1-execution-facts`): oxlint bans `as` casts, build-script literal is untouchable, conventional commits, PR-per-feature with CI + Claude review threads resolved before merge.
- The M1 review-established projection guarantees hold: `advance`, element style fields etc. are **non-null** (coalesced in GROQ); `elements`, `outro`, `leadCapture`, `theme`, `screenshotMobile`, `duration`, `mobile` member values, and **`image.alt`** (nullable in the type despite schema-required — coalesce to `''` at the image boundary) **can be null** — handle every null the types declare.

## Component / DOM contract

```
<div class="gt-tour" style="--gt-accent:…" data-gt>        ← theme props inline (M4 wires the theme doc; M2 sets only user-supplied overrides via a `style` prop passthrough)
  <div class="gt-header">
    <h2 class="gt-title">                                   ← tour.title (personalized)
    <div class="gt-progress" role="progressbar" aria-valuemin/max/now>
    <nav class="gt-chapters">                               ← chapter menu (settings.showChapterMenu)
  <div class="gt-stage" tabindex="-1">                      ← focus target on step change
    <figure class="gt-step">
      <img class="gt-screenshot" …>
      <div class="gt-elements">                             ← absolutely positioned children
        <button class="gt-hotspot" style="left:x%;top:y%">
        <span class="gt-tooltip-anchor"><button class="gt-tooltip-trigger" aria-expanded aria-controls><div class="gt-tooltip" role="group" id=…>
        <div class="gt-overlay" style="left:…;width:…">
  <div class="gt-controls">
    <button class="gt-prev"> <span class="gt-counter"> <button class="gt-next">
    <ol class="gt-dots">                                    ← settings.showStepDots
  <div class="gt-live" aria-live="polite" class~="gt-visually-hidden">
</div>
```

Positioning invariant: elements are positioned by percentage (`left: x%; top: y%; transform: translate(-50%, -50%)`) inside `.gt-elements`, which overlays the screenshot exactly (`.gt-step { position: relative }`).

### Task 3: events.ts + session.ts

**Files:** Create `src/react/events.ts`, `src/react/session.ts`; Test `test/react/events.test.ts`

**Interfaces (produces):**
```ts
// events.ts — exactly spec §8.4
export type GuidedTourEvent =
  | {type: 'tour_started'; tourId: string; sessionId: string}
  | {type: 'step_viewed'; stepIndex: number; stepKey: string; chapterIndex: number}
  | {type: 'element_clicked'; elementType: string; elementKey: string}
  | {type: 'cta_clicked'; label: string; href: string}
  | {type: 'lead_submitted'}
  | {type: 'tour_completed'; stepsViewed: number; durationMs: number}
  | {type: 'tour_abandoned'; lastStepIndex: number; durationMs: number}
export type GuidedTourEventHandler = (event: GuidedTourEvent) => void

// session.ts
export function createSession(): {sessionId: string; startedAt: number}
// createTracker(handler?) returns emit + finalize helpers enforcing ordering:
export function createTracker(handler: GuidedTourEventHandler | undefined, tourId: string): {
  start(): void                       // emits tour_started once, idempotent
  stepViewed(s: {stepIndex: number; stepKey: string; chapterIndex: number}): void
  elementClicked(e: {elementType: string; elementKey: string}): void
  complete(stepsViewed: number): void // emits tour_completed once; blocks later abandoned
  abandon(lastStepIndex: number): void// emits tour_abandoned once unless completed
}
```

`durationMs` measured from `createSession().startedAt` using `Date.now()` (allowed here — this is product code, not a workflow script). No storage of any kind.

TDD: randomUUID format; start idempotent; ordering (start emitted before first stepViewed even if stepViewed called first — tracker auto-starts); complete-then-abandon emits nothing on abandon; abandon-then-complete blocked too; undefined handler = all no-ops without throwing.

Behavior: uncontrolled by default (internal state, `defaultStep` not needed — start at 0); controlled when `step` prop is a number (state mirrors prop; interactions call `onStepChange` and do not self-mutate). Header shows personalized title; progress bar when `settings.showProgress`; chapter menu renders a button **only for chapters that contributed at least one `FlatStep`** (zero-step chapters get no button), and as a second guard a `firstStepOfChapter` result of `-1` is a no-op, never passed to navigation; dots when `settings.showStepDots`. Step counter uses the `stepCounter` label template. Tracker from Task 3 wired: mount → `start()` + first `stepViewed`; every change → `stepViewed`; reaching past the last step via Next on the final step → `complete()`; unmount without completion → `abandon()` (in the effect cleanup). Empty tour (no steps) renders a `.gt-empty` placeholder and emits nothing.

`styles.css`: full stylesheet for the DOM contract above — layout, custom-property defaults on `.gt-tour`, hotspot pulse `@keyframes`, `.gt-visually-hidden` utility, `@media (prefers-reduced-motion: reduce)` killing pulse/transitions. Class names only (`gt-` prefix), no element selectors, no `!important`.

TDD (Testing Library): renders title/screenshot; uncontrolled next/prev updates counter; controlled mode calls `onStepChange` and does not advance by itself; chapter jump; dots render one per step and navigate; empty tour placeholder; events sequence on mount/advance/unmount (spy handler); label overrides applied.

### Task 5: Hotspot + advance modes

**Files:** Create `src/react/Hotspot.tsx`; Modify `src/react/Step.tsx` (render elements), `src/react/GuidedTour.tsx` (advance-mode logic); Test `test/react/advance.test.tsx`

Behavior per spec §6:
- `advance='hotspot'` (default): clicking a hotspot with `action='advance'` goes to next step; the Next button **remains functional** (spec: controls available in every mode).
- `advance='button'`: hotspot `action='advance'` clicks do NOT advance (they emit `element_clicked` only).
- `advance='auto'`: `setTimeout(duration * 1000)` advances; timer resets on manual navigation; cleared on unmount; **suspended** when `document.visibilityState === 'hidden'`? — NO (YAGNI, not in spec): keep it a plain timer, note in code comment.
- Hotspot `action='reveal'`: toggles the nearest tooltip — implemented as: reveal opens the tooltip whose Euclidean distance (x/y percentage space) to the hotspot is smallest; no tooltips → no-op. `action='link'`: renders an `<a class="gt-hotspot" role/appearance identical>` with `href` (NOT personalized — URL invariant), `target="_blank"`, `rel="noopener noreferrer"`.
- Accessible name: `label` when set, else the `hotspotAdvance` / `hotspotReveal` / `hotspotLink` labels (already defined on `GuidedTourLabels` in Task 4 — this task only consumes them).
- `pulse && !prefersReducedMotion` → `.gt-hotspot--pulse` class (CSS handles the media query too; class is belt-and-braces for the animation).
- Every hotspot interaction emits `element_clicked {elementType:'hotspot', elementKey:_key}`.

TDD: all three advance modes (fake timers for auto — `bun test` supports `setSystemTime`/`jest.useFakeTimers` equivalents via `bun:test`'s `setSystemTime`; if timer mocking is unreliable, use 50ms durations and real waits), link element attributes incl. rel/target and un-personalized href, reveal targeting nearest tooltip, event payloads.

- [ ] Failing tests → implement → green → commit `feat: hotspots and step advance modes`
